## 一、产品背景

### 1.1 学 SQL 的三个真实困境

| 困境 | 具体表现 |
|---|---|
| **没有数据可练** | 教程里只有 `employees` 表 8 行数据，`SELECT *` 就完事了，练不出手感 |
| **题库表结构失真** | 练习题永远 2–3 张表、字段干净、没有空值、没有脏数据。真实生产库里换表导致表底跳变、冲正交易、估抄电量才是常态 |
| **练的和面试考的不一样** | 练习题教"查第 N 高的薪水"，面试问"算台区线损率""统计贷款五级分类不良率""找连续 4 个月欠费用户"——这些在普通练习站里根本找不到 |

### 1.2 机会点

市面产品分两类，都有缺口：

- **刷题型**（LeetCode / HackerRank）：表结构假、题目脱离业务、判题只认单一答案
- **模拟机型**（DataGrip 沙箱 / sqliteonline）：有真实数据但没有题目、没有引导、没有反馈

**本产品占据中间地带：行业真实数据 + 业务级题目 + 智能判题 + 分级引导。**

### 1.3 目标用户

| 画像 | 描述 | 核心诉求 |
|---|---|---|
| **P1 电力/能源数据岗求职者**（主用户） | 目标国网、南网、能源集团数据/信息化岗 | 熟悉营销、采集、线损、电费口径的 SQL 实操 |
| **P2 银行科技岗求职者** | 目标银行数据仓库、风控、零售条线 | 掌握账户、流水、五级分类、逾期指标 |
| **P3 在职数据从业者** | 已在行业内但写复杂分析靠"拼" | 系统掌握窗口函数、CTE，学会性能优化 |
| **P4 转行求职者** | 有 SQL 基础，想找最"硬"的行业场景练手 | 用行业真实口径武装简历与面试 |

## 二、产品定位

### 2.1 一句话定位

> **用两个行业（电网、银行）的"像生产环境一样脏"的数据库练 SQL——从语法、业务口径到性能优化，练完能直接上机面试。**

### 2.2 不是什么（明确排除）

- ❌ 不是 SQL 教程网站（以练为主，讲解只作为卡住时的辅助）
- ❌ 不是 LeetCode 式刷题站（不做算法题式的干净小表）
- ❌ 不是通用数据库客户端（不做连接任意数据库、DDL 管理）
- ❌ 不做 SQL 自动生成（必须用户自己写，这是产品存在的意义）

### 2.3 核心亮点（差异化）

| # | 亮点 | 说明 |
|---|---|---|
| 1 | **行业内行才懂的表格结构** | 电力有「变电站→线路→配变台区→用户→计量点」五级链；银行有「网点层级→客户→账户→流水→贷款→还款计划」 |
| 2 | **真实感脏数据** | 电力：换表跳变、估抄、倍率漏乘、线损为负；银行：冲正交易、余额不连续、五级分类与逾期天数不匹配 |
| 3 | **业务口径题** | 电力：线损率、电费回收率、峰谷平电量、欠费账龄；银行：日均存款、不良率、DPD 分箱、可疑交易 |
| 4 | **多解判题** | 比对**结果集**而非 SQL 文本，JOIN 写的和子查询写的都判过 |
| 5 | **分级提示不给答案** | 卡住给方向，不给成品代码 |
| 6 | **报错翻译成人话** | `no such column: cust_id` → "customers 表里没有 `cust_id`，你要找的可能是 `customer_id`" |
| 7 | **性能题（L5）** | 看 `EXPLAIN QUERY PLAN`、加索引、比耗时——面试区分度最高的一环 |
| 8 | **时序数据练习** | 电力 96 点负荷曲线、银行日终余额快照——练窗口函数与时间序列的最佳素材 |
| 9 | **AI 点评（V2）** | LLM 点评写法与优化建议（同时是 AI 应用能力的练习素材） |

## 三、技术架构

```
┌──────────────────────────────────────────────────────┐
│  浏览器（React + Vite + CodeMirror 6）                │
│  ┌─────────────┐  ┌──────────────┐  ┌─────────────┐  │
│  │ 题面面板     │  │ SQL 编辑器    │  │ 结果表格     │  │
│  └─────────────┘  └──────────────┘  └─────────────┘  │
│         │                │                 ▲         │
│         │                ▼                 │         │
│         │      ┌────────────────────┐      │         │
│         └─────▶│ 沙箱层 sql.js/WASM │──────┘         │
│                │ （SQLite 内存库）   │                │
│                └────────────────────┘                │
│         ▼  判题引擎（结果集归一化比对）                 │
│  ┌────────────────────────────────────┐              │
│  │ 进度存储 localStorage / IndexedDB   │              │
│  └────────────────────────────────────┘              │
└────────────────────────┬─────────────────────────────┘
                         │ 仅 L5 性能题 / 大库模式
                         ▼
        ┌────────────────────────────────────┐
        │ Node + Express + better-sqlite3     │
        │ 大库（千万行级）+ EXPLAIN 支持        │
        └────────────────────────────────────┘
```

### 3.1 关键技术决策

| 决策点 | 选择 | 理由 |
|---|---|---|
| SQL 在哪执行 | **双层**：常规题浏览器 WASM；L5 性能题走后端 | WASM 零延迟无并发压力；性能题需要真实磁盘与 EXPLAIN |
| 数据库引擎 | **SQLite**（前后端同方言） | 单文件、免安装、方言足够覆盖面试 |
| 沙箱安全 | WASM 每次重置；后端只读连接 + 语句白名单 | 杜绝 `DROP TABLE` / `DELETE` 破坏数据集 |
| 数据生成 | Python 脚本 + **固定随机种子** | 数据可复现 → 答案可自动化校验 |
| 题目定义 | 每题一个 JSON 文件（含 `scene` 字段） | 加题不改代码，多场景共用引擎 |
| 进度存储 | V1 localStorage，V2 再上账号 | 免登录即可开始练 |

### 3.2 多场景引擎抽象（重要）

两个场景**共用同一套引擎**，差异只在数据与题目：

```
public/scenes/
├── power/          # 电力场景
│   ├── power.sqlite       # 沙箱库（小库）
│   ├── schema.json        # 表结构元数据（喂给数据字典页与自动补全）
│   └── dirty_report.json  # 脏数据实测比例（验收用）
└── bank/           # 银行场景
    ├── bank.sqlite
    ├── schema.json
    └── dirty_report.json

public/problems/
├── power/*.json    # 电力题目（30 题）
└── bank/*.json     # 银行题目（30 题）
```

## 四、场景一：电力（电网营销 / 用电采集）

### 4.1 业务背景设定

> 你是某省电力公司营销部的数据分析员。要处理从**变电站 → 输电线路 → 配变台区 → 用户 → 计量点**的完整档案链，以及抄表电量、电费账单、缴费流水、停电事件、抢修工单、96 点负荷曲线等数据。

### 4.2 表清单（12 张）

| 表 | 行数（小库） | 说明 |
|---|---|---|
| `org_units` | 200 | 供电单位，**四级层级**（省→市→县→供电所），`parent_id` 自关联 |
| `stations` | 300 | 变电站：电压等级、主变容量、投运日期 |
| `lines` | 800 | 线路：所属变电站、电压等级、长度 |
| `transformers` | 3,000 | **配变台区**：所属线路、容量、状态（在运/停运/退役） |
| `customers` | 20,000 | 用户档案：用户类别、行业、所属台区、状态（在运/暂停/销户） |
| `meters` | 22,000 | 计量点/电能表：资产编号、**CT 倍率**、检定日期、状态 |
| `meter_readings` | 240,000 | 抄表电量（近 12 个月）：抄见/估抄/远抄、表底、本期电量、有功无功 |
| `bills` | 240,000 | 电费账单：电量、电度电费、基本电费、**力率调整电费**、总电费、缴费状态 |

### 4.4 故意设计的"脏数据"清单（电力场景核心资产）

| # | 脏数据类型 | 比例 | 逼你练出什么 |
|---|---|---|---|
| 1 | **换表导致表底跳变**（换表后新表底从 0 开始） | 2% | 别用 `curr - prev` 直接算电量，要看表计状态 |
| 2 | **CT 倍率漏乘**（部分记录未乘倍率，电量偏小 20–100 倍） | 1.5% | 电量口径校验、异常值识别 |
| 3 | **估抄电量**（`read_type='估抄'`，电量是推算的） | 8% | 分析时是否剔除估抄数据 |
| 4 | 销户用户仍有电量与电费记录 | 5% | 口径定义：有效用户怎么算 |
| 5 | 抄表日期不固定（1–25 号漂移） | 100% | 按账期而非按日期聚合 |
| 6 | 停电事件时间重叠（同一台区两条重叠记录） | 6% | 重叠区间合并、去重 |
| 7 | 工单 `finish_time` 早于 `create_time` | 0.5% | 数据质量核查 |
| 8 | 96 点曲线**缺失采样点**（采集失败） | 3% | 缺失值处理、`COUNT` 校验 |
| 9 | 台区**线损率为负**（供电量 < 售电量） | 4% | 异常检测、业务解释 |
| 10 | 欠费但 `pay_status='已缴'`（对账遗留） | 2% | 多表交叉验证 |
| 11 | 电压等级/容量为 NULL（新投运设备档案不全） | 3% | `COALESCE`、默认值处理 |
| 12 | 同一用户同期两条账单（重复出账） | 0.8% | 去重、`ROW_NUMBER` |

> **设计原则：每一处脏数据都必须在某道题里被"逼出来"**，不为脏而脏。验收时用脚本统计实测比例。

### 4.5 电力场景题目示例

| 级别 | 题目 | 考察点 |
|---|---|---|
| L1 | 统计各用户类别的用户数、在运用户数（剔除销户） | `WHERE`、条件聚合 |
| L2 | 统计每个供电所的电费应收、实收与**回收率** | 多表 JOIN、层级归属、比率计算 |
| L2 | 列出每个台区的用户数与总容量，按用户数降序 | `GROUP BY` + `JOIN` 到台区 |
| L3 | **计算各台区月度线损率**，找出线损率 > 10% 或 < 0 的异常台区 | 供电量/售电量口径、异常检测 |
| L3 | 计算欠费用户账龄（欠费月份数、欠费总额），分箱统计 | 日期差、条件聚合、`CASE WHEN` 分箱 |
| L3 | 按阶梯电价规则计算居民用户当月电费并与账单比对（找差异） | 复杂 `CASE`、多表交叉验证、脏数据识别 |
| L4 | 从 96 点曲线计算每个计量点的**峰、平、谷电量**与最大负荷时刻 | 窗口函数、`CASE` 时段划分、`ROW_NUMBER` 取峰值 |
| L4 | **找出连续 3 个月欠费的用户**及其起始月份 | 经典"连续行为"题 |
| L4 | 用递归 CTE 展开四级供电单位树，汇总各单位用户数 | `WITH RECURSIVE` |
| L5 | 优化"台区线损计算"查询（原查询 4.1 秒），并解释优化点 | `EXPLAIN QUERY PLAN`、索引、执行顺序改写 |

**L3 线损率题详细规格（示例，展示题目颗粒度）**

```
题目：计算 2024 年 6 月各配变台区的线损率

业务背景：线损率 = (供电量 - 售电量) / 供电量 × 100%。
        供电量 = 台区总表抄见电量；售电量 = 台区内所有用户抄见电量之和。
        营销部要求线损率 > 10% 的台区要现场核查。

要求：输出 台区编号、台区名称、供电量、售电量、线损率（% 保留 2 位），
     仅输出线损率 > 10% 的台区，按线损率降序。

期望列：transformer_id, transformer_name, supply_kwh, sale_kwh, loss_rate
注意：- 剔除估抄电量（read_type='估抄'）
     - 销户用户当月有电量的也要计入售电量（历史口径）
     - 线损率为负的台区也属于异常，本题只要 > 10% 的

预计用时：12 分钟
考点：多表 JOIN / 条件聚合 / 类型转换 / 比率计算
常见错误：忘记剔除估抄 → 线损率虚高；用 WHERE 过滤销户 → 售电量偏小
```

## 五、场景二：银行（零售银行 / 信贷风控）

### 5.1 业务背景设定

> 你是某商业银行数据仓库团队的开发工程师。要处理**总行→分行→支行**三级机构下的客户、账户、交易流水、贷款、还款计划、信用卡、存款日均、理财持仓等数据，支撑存款分析、信贷资产质量、反洗钱可疑交易识别等需求。

### 5.2 表清单（12 张）

| 表 | 行数（小库） | 说明 |
|---|---|---|
| `branches` | 200 | 机构，**三级层级**（总行→分行→支行），`parent_id` 自关联 |
| `employees` | 1,200 | 员工/柜员/客户经理：所属机构、岗位 |
| `customers` | 20,000 | 客户：个人/对公、风险等级、开户机构、AUM |
| `accounts` | 35,000 | 账户：活期/定期/对公结算、币种、余额、利率、状态 |
| `transactions` | 150,000 | **交易流水**：借贷方向、金额、交易后余额、渠道、对手方、状态 |
| `loans` | 8,000 | 贷款：类型、本金、余额、利率、期限、还款方式、状态 |
| `loan_repayments` | 60,000 | 还款计划与实还流水：期次、应还本息、实还日期与金额 |
| `overdue_records` | 12,000 | 逾期记录：逾期日期、**逾期天数 DPD**、五级分类 |
| `credit_cards` | 15,000 | 信用卡：额度、已用额度、账单日、到期还款日 |
| `card_statements` | 120,000 | 信用卡账单：账期、账单金额、最低还款、已还金额 |
| `deposits_daily` | 155,000 | **存款日终快照**：账户 × 31 天（算日均余额用） |
| `wealth_holdings` | 25,000 | 理财持仓：产品、金额、买入/赎回日期、收益 |

### 5.3 核心字段设计（节选）

**`transactions` 交易流水**

| 字段 | 类型 | 说明 |
|---|---|---|
| txn_id | INT PK | |
| account_id | INT | |
| txn_time | TEXT | 交易时间（**含时分秒**，1 天内分布不均） |
| value_date | TEXT | 记账日期 —— **可能与 txn_time 不同日（跨日/节假日）** |
| direction | TEXT | D（借记/出账）/ C（贷记/入账） |
| amount | REAL | 交易金额（**单位：元，两位小数**） |
| balance_after | REAL | 交易后余额 —— **4% 的记录与流水累加不一致（快照 bug）** |
| txn_type | TEXT | 转账/消费/取现/工资代发/缴费/理财申购 |

| 级别 | 题目 | 考察点 |
|---|---|---|
| L1 | 统计各账户类型开户数与总余额，剔除销户账户 | `WHERE`、聚合 |
| L2 | 统计各分行（含下属支行归并）的存款余额与客户数 | 层级归并、JOIN |

| L3 | **计算各机构贷款五级分类分布与不良率**（不良 = 次级+可疑+损失） | `CASE` 分类、比率、口径定义 |

**L3 不良率题详细规格（示例）**

```
题目：计算 2024 年 6 月末各分行的贷款不良率

业务背景：不良率 = 不良贷款余额 / 贷款总余额 × 100%
        不良贷款 = 五级分类中的「次级 + 可疑 + 损失」
        注意：核销贷款（status='核销'）不计入总余额

要求：输出 分行名称、贷款总余额（万元）、不良余额（万元）、不良率（% 保留 2 位），
     按不良率降序。仅统计 2024-06-30 有逾期记录或状态非结清的贷款。

期望列：branch_name, total_balance_wan, npl_balance_wan, npl_rate
易错点：- 用 INNER JOIN 关联逾期表会丢掉「正常」类贷款，导致分母偏小、不良率虚高
       - 单位换算（元 → 万元）漏做或做两次
       - 忘记剔除核销贷款

预计用时：10 分钟
```

### 6.3 判题规则（核心模块）

```
用户 SQL
  → ① 安全校验（只允许 SELECT / WITH，拒绝 DDL/DML/PRAGMA 写操作）
  → ② 执行（超时 5s，最多返回 1000 行）
  → ③ 结果集归一化
  → ④ 与参考答案结果集比对
  → ⑤ 三态反馈
```

**归一化规则：**

| 维度 | 规则 |
|---|---|
| 列名 | **不敏感**（按列位置比对），列数必须一致 |
| 行顺序 | 默认**不敏感**；题目 `order_sensitive: true` 时才校验 |
| NULL | 统一标记，`NULL = NULL` 视为相等 |
| 浮点 | 按题目指定精度四舍五入（默认 4 位；百分比题默认 2 位） |
| 字符串 | 去首尾空格；默认区分大小写 |
| 时间 | 统一转为 `YYYY-MM-DD` 后比较 |

**三态反馈：**

| 状态 | 触发 | 用户看到 |
|---|---|---|
| ✅ 通过 | 结果集完全一致 | "通过！还可以试试用 CTE 分步写，可读性更好" |
| 🟡 接近 | 列数行数对、部分值不符 | **高亮差异单元格**："你算出线损率 8.2%，期望 12.4%——是不是把估抄电量也算进去了？" |
| 🔴 失败 | 列数/行数/报错 | "你返回了 7 列，题目要 5 列"；报错翻译：`no such column: cust_id` → "customers 表用的是 `customer_id`" |

| 峰谷平 | 一日内按电价时段划分的电量（峰段贵、谷段便宜） |
| 供电量/售电量 | 台区总表电量 / 台区内用户电量之和 |
